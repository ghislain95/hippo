# Design

## Context

See proposal.md for the motivation and the decisions already taken with Ghislain (schedule in Paris time, image copy, 384 MiB container, guards, submission protocol, tables). This design settles how they are built.

Current state that shapes the approach:

- Items stop at `extracted` (`internal/extraction`). The only background task is the extraction worker, started and stopped by `cmd/hippo` with its own context (`backend/cmd/hippo/main.go`).
- Heavy parsing already runs in a child process of the same binary (`hippo extract-page`, `internal/extraction/child.go`): memory watch through `runtime/metrics`, exit code 86 above the limit, explicit environment (`GOMAXPROCS=2`), `Pdeathsig` on Linux, output bounded by `cappedBuffer`, a PDF handed as descriptor 3. The image copy needs the same machinery.
- `DATA_DIR/tmp` (`extraction.TempDir`) creates files whose name is removed at once (two descriptors, one read-only) and sweeps leftovers at start-up.
- `assetfs.Dir.Open(rel)` opens a stored image through `os.Root`; `assetfs` is a leaf imported only by `httpapi` and `cmd/hippo`.
- `store.createUser` runs on a `*sql.DB` or a `*sql.Tx` (`execer`); `CreateUser` is called by tests only, `EnsureSingleUser` by `cmd/hippo`. `nextChangeSeq` is the only writer of `sync_sequence`.
- `internal/analysis/schema` embeds the bundled `classify_item` schema, generated by `cmd/schemabundle` (`x-schema-version` 1 at its root). `system-prompt.md` holds the fixed part (prompt version 3) and the formats of the référentiel and of the item message; nothing in the backend reads it yet.
- `config.Config` already has `AnthropicAPIKey` (optional), `AnalysisModel`, `BatchSchedule` (unvalidated string), `MonthlyBudgetUSD`. `capture.LoadParis` loads Europe/Paris from the embedded tz database.
- `anthropic-sdk-go`, `golang.org/x/image` and `github.com/gen2brain/h265` are approved (proposal, 2026-11-06) but none is in `backend/go.mod` yet. `golang.org/x/image@v0.47.0` is in the local module cache (indirect); the two others are not, so every claim about them below is **unverified** and has a verification task. (Slice 3: `golang.org/x/image` v0.47.0 and `github.com/gen2brain/h265` v0.2.4 are now required and verified in D10; the SDK stays unverified until task 5.1.)

## Goals / Non-Goals

**Goals:**

- One pass per Paris date that sends each user's waiting items in one Message Batches batch, with the guards, the request format and the private-item guarantee of the specs.
- Bounded memory: the parent never holds a batch body; one image decoded at a time, in a bounded child.
- No double send except one documented, logged case.
- The child-process code shared without changing the extraction's behaviour.

**Non-Goals:**

- Anything E3-02 to E3-08 owns (proposal, Non-goals). In particular no store function writes `cost_usd` or tokens: tests that need them use a `storetest` SQL helper, like `SetAnalysisState`.
- Validating `BACKUP_SCHEDULE` (E6 owns the backup).
- The normalised-name index of categories (E3-03), the depth check of a category written by the user or the AI (E3-03, E4).

## Decisions

### D1. Daily schedule in Paris time (`internal/schedule`)

- `ParseDaily(expr) (Daily, error)` accepts exactly five space-separated fields `M H * * *`, `M` in 0–59 and `H` in 0–23 as plain decimal integers; anything else (lists, ranges, steps, names, a non-`*` day, month or weekday field, six fields) is an error. `config.Load` calls it, so an invalid `BATCH_SCHEDULE` stops the start-up with an error naming the variable; `Config.BatchSchedule` becomes a `schedule.Daily`.
- `Daily.RunAt(date, loc) time.Time` gives the single run instant of a Paris calendar date:
  - the earliest instant whose wall clock in `loc` is that date at `H:M` (in the autumn overlap, the first of the two, CEST);
  - when no such instant exists (spring gap), the first instant of that date whose wall clock is after `H:M`, which is the end of the gap (03:00 CEST).
  - It does not rely on `time.Date` for this: Go documents that in a transition « it does not guarantee which » instant it returns (`$GOROOT/src/time/time.go:1726-1734`, go1.27.3). `RunAt` checks the candidate and its neighbours one hour apart and picks by the rule above.
- `Daily.Next(after, loc)` is the first `RunAt(d)` strictly after `after`, for `d` = the Paris date of `after`, then the following dates. Each date has exactly one instant, so the overlap never runs twice, even across a restart, and a restart never catches up a missed date (Non-goal).
- `Run(ctx, daily, loc, clock, pass)` loops: compute `Next(clock.Now())`, wait on `clock.After(next − now)` or `ctx.Done()`; on wake, if `clock.Now()` is still before `next` (wall clock moved back), wait again; otherwise run `pass(ctx)` synchronously and loop from `Next(next)`. The clock is an interface (`Now`, `After`), real in production, fake in tests that fire it explicitly (no sleep, docs/dev/testing.md « Horloge »).
- `cmd/hippo` starts `Run` in a goroutine with its own cancellable context, like the extraction worker, and waits for it before closing the store. A pass interrupted by the stop is handled by D7.
- Alternatives rejected: a cron library (new dependency for one daily form; no control of the DST rule); `TZ`-driven local time (the distroless image has no zone database; the domain already uses `LoadParis`); remembering the last run date in memory or in the base (unnecessary once each date has a single instant).

### D2. Selection

- Users come from `store.UserIDs`; everything below is per user, every query filtered by `user_id` (RG-90).
- `store.AnalysisQueue(ctx, userID, limit)` returns (as `[]store.AnalysisQueueItem`) at most 200 items with `status = 'extracted' AND is_private = 0 AND deleted_at IS NULL`, `ORDER BY id` (ULIDs from the store clock: creation order, and the order E3-02 retries keep). It returns what the message needs except the content (kind, url, site, title, extraction mode, truncation, note, `incomplete_retried`, `is_private`, assets); the content is read per item with the existing `ItemContent` while the request is written, so only one content is in memory at a time. New index `items_user_status ON items (user_id, status, id)`.
- 200 MiB body cap (209 715 200 bytes; the API's 256 MB limit, unverified at the SDK version, under either reading of « MB »): each request is appended to the segment file (D6); when the file would pass the cap, it is truncated back to the previous request and the selection stops there. The item left out stays `extracted`, as does every later one. The cap is a field of the pass options so a test can lower it (spec scenario « Beyond the body limit »).

### D3. Guards, in this order, before any read of item content

1. No `ANTHROPIC_API_KEY` → `cmd/hippo` builds no `Analyzer`; the pass logs `reason=no_api_key` once per pass and stops. Reconciliation is skipped too.
2. Reconciliation of the user's `pending` batches runs (D8), then `store.HasBatchWithoutCost(ctx, userID)`: a batch of the user with `status IN ('pending','in_progress')` or `status = 'ended' AND cost_usd IS NULL` → `reason=cost_pending`. `failed` batches never block: nothing was billed, except the ambiguous reconciliation case (Risks).
3. `store.MonthSpend(ctx, userID, from, to)`: `SUM(cost_usd)` of the user's batches with `created_at` in `[from, to)`, the bounds being midnight of the first day of the current and next Paris month, converted to UTC. `spent >= MonthlyBudgetUSD` → `reason=budget_reached`. A batch counts in the month it was **created** (sent), not the month it ends. The comparison is the same as RG-81's (`>=`), so a budget of 0 never sends.

Each refusal logs `user_id`, `reason`, and the count of waiting items only (no content). The check happens before the batch is built: no image is decoded for a pass that will not send.

### D4. Request format

The body is the Message Batches create body `{"requests":[{"custom_id":…,"params":{…}}]}`, written by `internal/analysis` itself with `encoding/json` (`SetEscapeHTML(false)`, so `<element>` stays readable and short), never through SDK types: the request bytes are ours, testable without the SDK, and streamed (D9).

`params`, keys in this order (the cache prefix is tools → system → messages; key order in JSON does not matter to the API, it only keeps the body readable):

- `model`: `cfg.AnalysisModel`.
- `max_tokens`: 4000, or 8000 when `incomplete_retried = 1` (RG-36).
- `tools`: one tool `{"name":"classify_item","description":<root description of the bundled schema>,"input_schema":<bundled schema as embedded>}`.
- `tool_choice`: `{"type":"tool","name":"classify_item"}`.
- `system`: two text blocks: the fixed part; then the référentiel with `"cache_control":{"type":"ephemeral"}`.
- `messages`: one `user` message (D5).

`custom_id` = item id (26-character ULID; the API's `custom_id` pattern is unverified, a test asserts the ULID alphabet fits `^[a-zA-Z0-9_-]{1,64}$`).

**Fixed part and prompt version.** `go:embed` cannot reach `docs/`, so `cmd/schemabundle` gains `-prompt <system-prompt.md> -prompt-out <file>` and writes `backend/internal/analysis/prompt/prompt.gen.json`: `{"prompt_version": 3, "fixed": "<the text of the first ```text fence under ## Partie fixe>"}`. The version is read from the `prompt_version = N` of the header line. The tool fails when either is missing or when there is not exactly one fence in that section. `-check` covers it like the bundle; the file joins `GENERATED`; its name ends in `.gen.json`, so the protect-files hook refuses a hand edit. Envelope version: `x-schema-version` at the root of the embedded bundled schema, read at start-up (start-up fails if absent). Alternatives rejected: a copy of the prompt in Go source (drifts silently); reading `docs/` at run time (not in the image).

**Référentiel** (built once per batch, per user, from `store.ContentTypes` and `store.Categories(userID)`):

```
<referentiel>
<types>
tech_article | Article technique
…
</types>
<categories>
1 | Dev | active | Développement logiciel : …
2 | Dev › Java & Spring | active |
…
</categories>
<tags>
</tags>
</referentiel>
```

- Types: non-deleted, `ORDER BY id` (ids 1–7 seeded in the §7 order); a proposed type gets ` | proposed`.
- Categories: non-deleted rows of the user (`store.Categories` returns them `ORDER BY id`; the builder makes the tree); roots `ORDER BY id`, each followed by its children `ORDER BY id`; path `parent › child`; status `active` or `proposed`; description empty when NULL, the line then ending with `|` (no trailing space). A child whose parent is deleted is not listed (cannot happen before E4; stated so the order stays total).
- Tags: empty block until E3-04. Newlines inside a name or description are replaced by a space so that one category stays one line.

### D5. The item message

One `user` message. For a link or a note, a single text block: the `<element>` block, then, when there is content, `\n<contenu>\n…\n</contenu>`. For an image, a text block with the `<element>` block, then one `image` block per asset (base64, `image/jpeg`), or none when the copy failed (D10).

`<element>` lines, in the order of `system-prompt.md`, absent fields left out:

| Line | link | note | image |
| --- | --- | --- | --- |
| `forme:` | `link` | `note` | `image` |
| `url:` | captured URL without its user info (`user:password@` removed, as the extraction does before its request); never the normalised URL | — | — |
| `site:` | `site_name` when set | — | — |
| `titre_original:` | `title` unless it equals the provisional title of the URL (RG-26, `capture.ProvisionalTitle`, exported rather than copied) | — | — |
| `extraction:` | `complète` (`full`), `repli sur les métadonnées` (`fallback`) | `aucune` | `aucune` |
| `contenu_tronqué:` | `oui` / `non` | — | — |
| `note_de_capture:` | `user_note` when set | — (the note text is the content) | `user_note` when set |
| `<contenu>` | `content_text` when set and non-empty | `user_note` (the note text) | — |

The label for `none` is `aucune`, without the « (image ou note) » of the format's comment, which describes when it applies. A multi-line note de capture stays as is, last line of the block. The prompt treats everything in `<element>` and `<contenu>` as data (prompt injection case of the eval set); the backend does not escape tags. An image's provisional title is not sent: it comes from the capture note or the date (RG-26), both already known to the AI; the proposal's « title and capture note » is the `<element>` block.

### D6. Building the body: segments, then the committed body

1. For each selected item, in order, the request JSON is appended to a **segment file**; its offset and length are kept in memory (`custom_id → [off, len)`). Text parts are marshalled; the image data is streamed from the image copy through a `base64.NewEncoder` into the file, never held whole. The 200 MiB cap is checked after each request (D2).
2. The submission transaction (D7) returns the ids it actually moved to `submitted`.
3. The **body file** is assembled from the segments of exactly those ids: `{"requests":[`, segments joined by `,` with `io.Copy` from an `io.SectionReader`, `]}`. Its size is known for the `Content-Length`.

Both are unnamed files of `DATA_DIR/tmp` (`TempDir.NewFile()`, exported by `extraction`; consumed by `analysis` through a one-method interface), so a crash leaves nothing on the NAS nor in the backups. They are closed when the send returns. Disk: at most twice 200 MiB for a moment; a write error (full disk) aborts the user's pass before the transaction, nothing is submitted, `reason=storage_unavailable`.

Why segments and a second file rather than building after the transaction: building is the slow part (image copies, seconds each); the transaction must be short and must be the last word on privacy (D11). Rejected: building the body after the transaction (items `submitted` for minutes while images decode; a crash then leaves `pending` batches for nothing); rewriting in place (no gain).

### D7. Submission protocol

1. Build segments (D6).
2. `store.SubmitBatch(ctx, userID, NewBatch{Model, PromptVersion, EnvelopeVersion}, ids)` in one `BEGIN IMMEDIATE` transaction:
   - re-reads `status`, `is_private`, `deleted_at` of each id **for this user**; keeps those still `extracted`, public and not deleted;
   - none kept → no row, returns empty (nothing is sent; no call is made, RG-31);
   - inserts `batches` (`id` ULID from the store clock, `status='pending'`, `item_count` = kept count, `created_at`);
   - for each kept item, `nextChangeSeq` then `UPDATE items SET status='submitted', batch_id=?, updated_at=?, change_seq=? WHERE user_id=? AND id=?`.
3. Assemble the body (D6) and send it once (D9).
4. Outcome:
   - **accepted**: `store.MarkBatchSent(userID, batchID, anthropicID)` sets `anthropic_batch_id`, `status='in_progress'`; a `UNIQUE` violation (the id is already recorded) is logged as an error and the row stays `pending` for reconciliation;
   - **refused** (the API answered an HTTP error status): `store.FailBatch(userID, batchID)`: in one transaction, every item of the user with `batch_id = ? AND status = 'submitted'` goes back to `extracted`, `batch_id = NULL`, new `updated_at` and `change_seq`, `attempts` unchanged (no attempt counted); the row becomes `failed`;
   - **unknown** (transport error, timeout, cancelled context, crash): nothing is written; the row stays `pending` and is reconciled (D8).
   Writes after the send use `context.WithoutCancel(ctx)` bounded to 10 s, as the extraction does, so a stop during the send still records an accepted batch.
- The send has its own 10-minute timeout (200 MiB at about 3 Mbit/s up).

### D8. Reconciliation of `pending` batches

Runs at start-up (in the background, after the store opens; not blocking the server) and at the start of each user's pass, only when the user has `pending` rows and an `Analyzer` exists.

- `Analyzer.ListBatches(ctx, since)` pages through the key's batches, newest first (ordering unverified at the SDK version; the loop does not depend on it: it stops at a page whose batches are all older than `since`, or after 10 pages), and returns `{id, created_at, request_count}` where `request_count` is the sum of the batch's `request_counts` (unverified field names).
- For each pending row, oldest first: candidates are listed batches with `created_at` in `[row.created_at − 10 min, row.created_at + 20 min]` (NAS clock skew, plus the send timeout), `request_count == item_count`, and not already the `anthropic_batch_id` of one of the user's rows.
  - exactly one candidate → `MarkBatchSent` (it is adopted; it leaves the pool for the next rows);
  - none, or more than one → `FailBatch`, logged at warn with `reason=possible_double_send`, `batch_id`, the count; the items go to the next pass.
- Listing fails → the row stays `pending`; the guard of D3 then blocks the user (`cost_pending`) until a later reconciliation succeeds.
- Residual risk, accepted in the proposal: a batch accepted by Anthropic but not matched (two users' pending batches of the same size in the same window, or a 5xx answered after creation) is sent again the next night: at most one double send per such row, always logged. With one user in V1 and a dedicated key, only the 5xx case remains.
- E3-02 must ignore a result whose `custom_id` is not an item of the batch's row (note for E3-02).
- Rejected: matching by `custom_id` (results unreadable until the batch ends); never reverting (items stuck `submitted` forever); reverting at once after a timeout (a slow accepted send then doubles every time).

### D9. Anthropic client behind `Analyzer`

```go
// internal/analysis
type Analyzer interface {
    CreateBatch(ctx context.Context, body io.ReadSeeker, size int64) (BatchRef, error) // BatchRef{ID string; CreatedAt time.Time}
    ListBatches(ctx context.Context, since time.Time) ([]BatchInfo, error)               // BatchInfo{ID string; CreatedAt time.Time; RequestCount int}
}
var ErrRejected = errors.New("batch rejected") // the API answered with an error status: the send definitely failed
```

E3-02 and E3-06 add their methods. `internal/analysis/anthropic.New(apiKey)` implements it:

- POST `/v1/messages/batches` with the body file as a raw body (`option.WithRequestBody("application/json", body)`, a request-level option of the Stainless-generated SDK), the `Content-Length` set from `size`, and **no retry** (`option.WithMaxRetries(0)`): an automatic retry of a create is a double send. **Unverified** at the SDK version to pin: the option names, that a raw `io.Reader` body is streamed and not buffered, and that `Content-Length` can be set (else chunked). Task 5.1 checks them in the installed source (`file:line` in this design). Fallback if the SDK buffers the body: a plain `net/http` POST from the same package with the SDK only for listing; the depguard rule is unchanged.
- An HTTP error status maps to `ErrRejected` (with the status code and the API error `type`, never the message, which may quote the request); everything else is an unknown outcome.
- List: the SDK's batch list with its default retries (a read).
- The key never reaches a log; the child processes never get the service environment.
- depguard `anthropic-only-in-analysis` narrows to `**/internal/analysis/anthropic/**`.
- Tests use a fake `Analyzer` in `internal/analysis/analysistest` that records each body (parsed back to JSON) and plays scripted outcomes (accepted, rejected, unknown, list results). No test calls the network.

### D10. Image copy (`internal/imagecopy`, child `hippo copy-image`)

**Child protocol** (same rules as `extract-page`: no configuration, no base, no log, stderr discarded, environment `GOMAXPROCS=2` only):

- descriptor 3: the stored image, read-only, opened by the parent through `assetfs.Dir.Open` (consumed by `analysis` as a one-method interface; `assetfs` stays a leaf);
- descriptor 4: the write end of an unnamed temporary file (D6's `NewFile`), where the child writes the JPEG; the parent reads it back through the read-only end;
- stdin: one JSON line `{"max_pixels":…,"long_edge":1568,"quality":85}` (constants of the parent, passed so tests can lower them);
- stdout: `{"reason":"ok"|"too_many_pixels"|"undecodable","width":…,"height":…,"peak_bytes":…}`, bounded to 4 KiB.
No path crosses the process boundary. One image at a time: the pass copies images sequentially, so at most one decoded image exists on the NAS at any moment.

**In the child**, in this order:

1. `image.DecodeConfig` (the format is sniffed from the bytes; formats registered: `image/jpeg`, `image/png`, `golang.org/x/image/webp` (`webp/decode.go:303,313`, registered at `:319`, v0.47.0), HEIC through `gen2brain/h265` (`heic/heic.go:921-928`)). `width × height > max_pixels` → `too_many_pixels` without decoding. Ceiling: **50 Mpx**, which admits the 48 Mpx « HEIF Max » photos of recent iPhones; its memory is measured (task 3.9) against the 256 MiB limit below, and lowered to 40 Mpx if a 48 Mpx HEIC does not fit.
2. `image.Decode`. GIF is not registered: capture never stores GIF (RG-02, `assets.mime_type` CHECK).
3. Scale, never up: when the long side is above 1568, an in-house **integer box reduction** by `k = floor(long / 1568)` (average of `k × k` blocks, fast paths for `*image.YCbCr` and `*image.RGBA`/`*image.NRGBA`, generic `At` otherwise) when `k ≥ 2`, then `draw.ApproxBiLinear` to the exact size (long side 1568, other side rounded). Why: `draw.CatmullRom` (and every `draw.Kernel`) allocates a `[][4]float64` of `dst width × src height` (`golang.org/x/image/draw/scale.go:204-205` at v0.47.0): 303 MB for a 48 Mpx photo, 59 MB for a phone screenshot. `ApproxBiLinear` alone has no buffer but aliases beyond a factor of 2 (text in a photographed page). The box step is the anti-aliasing filter; afterwards the factor is below 2. Peak: decoded source + at most a `2×1568`-side RGBA (39 MB) + the 1568-side RGBA (10 MB).
4. Orientation, applied on the small image (cheap): JPEG EXIF `Orientation` (tag 0x0112, values 1–8) read by an in-house parser of the APP1 `Exif` segment (TIFF header, both byte orders, IFD0 only, every offset bounds-checked, 64 KiB max) — the standard decoder ignores APP1 (`$GOROOT/src/image/jpeg/reader.go:640-642`, go1.27.3); HEIC `irot`/`imir` read by an in-house bounded reader of the primary item's `pitm`/`ipco`/`ipma` (129 lines of code, under the ~150 of this design), since h265 applies them only to a full-size NRGBA image (« Verification » below). PNG and WebP: no orientation.
5. Transparency is flattened on white; the result is encoded with `image/jpeg` quality 85, which writes only DQT, SOF0, DHT and SOS segments (`$GOROOT/src/image/jpeg/writer.go:575-634`, go1.27.3): no EXIF, XMP, ICC nor comment reaches the copy.

**Limits**: child memory limit 256 MiB (soft limit 200 MiB), timeout 30 s, output JPEG at most 5 MiB (the API's per-image limit, unverified) else no image. Any other outcome (exit 86, timeout, crash, garbage, `too_many_pixels`, `undecodable`, oversized output, asset file missing) → the request is written without image block, logged with `item_id`, `asset_id`, `reason` (`too_many_pixels`, `undecodable`, `too_large`, `timeout`, `copy_failed`, `asset_missing`); the pass continues. A child that cannot start (binary missing, `fork` refused) aborts the user's pass before the transaction (`reason=copier_unavailable`), as the extraction leaves an item queued, rather than sending images as partial content.

**HEIC dependency**: `github.com/gen2brain/h265` as approved. Task 3.2 verifies, before any code, that this module path exists, decodes HEIC/HEIF stills (not only raw H.265 streams), handles **grid** images (iPhone photos are tiled), builds with `CGO_ENABLED=0`, and how it registers with `image.RegisterFormat`. If it does not (for example if the HEIC decoder is the separate module `github.com/gen2brain/heic`), stop and ask Ghislain: it is a different dependency. Impact if HEIC fails anyway: limited, since the app and the share extension send JPEG (backlog E2-04); a HEIC is then sent without image.

**depguard**: new rule `image-decoding-only-in-imagecopy` denies `golang.org/x/image` and `github.com/gen2brain` outside `**/internal/imagecopy/**`.

**Verification of the dependencies (tasks 3.1 and 3.2, 2026-11-06, from the installed sources):**

- `golang.org/x/image` **v0.47.0** (latest release): `makeTmpBuf` still allocates `dw × sh` `[4]float64` (`draw/scale.go:204-205`); `webp.Decode` `webp/decode.go:303`, `DecodeConfig` `:313`, `image.RegisterFormat("webp", "RIFF????WEBPVP8", …)` `:319`. No cgo.
- `github.com/gen2brain/h265` **v0.2.4** (latest release). The module path exists (`go.mod:1`); the HEIC decoder is its package `github.com/gen2brain/h265/heic`, in the same module (README « Decoding »), not a separate `gen2brain/heic`: no other dependency.
- **Stills and grids**: the primary item is decoded with any `grid` it derives from (`heic/heic.go:568-570` `decodeItemImage`, `heic/grid.go:59` `decodeImage`, tiles decoded in parallel); README « Supported » lists `grid`, `clap`/`irot`/`imir`. Checked on `grid.heic` (12 tiles of 512 × 512, made by `sips`) and a 48 Mpx `sips` HEIC (tiles of 896 × 1024).
- **Registration**: `init` registers the format `heic` for the brands `heic heix heim heis hevc hevx hevm hevs mif1 msf1` (`heic/heic.go:921-928`), with `decodeWrapper` (`:834`, reads the whole file, then `Decode` without options) and `configWrapper` (`:849`); `heic.DecodeConfig` (`:732`) parses the header only (`parseHeader`, `:275`) and gives the size of the image item (`ispe`, inside any `clap`, `:813-831`), before any `irot`: not the size of the coded frames the decoder allocates, which come from the HEVC SPS and are bounded only by `Options.FrameSizeLimit` (default 16384², `:96`; `hevc/decoder.go:118-120,280-283`; the grid's output is bounded by the same limit, `heic/grid.go:75-77`).
- **`irot`/`imir`**: applied only under `Options.AutoRotate` (`heic/heic.go:114-116`; `heic/transform.go:138-179`, a full copy for a quarter turn, `:52-77`), which forces NRGBA and refuses a Y′CbCr image (`transform.go:152-154`); not exposed otherwise. `image.Decode` never applies them (`decodeWrapper`). Hence the in-house reader; `imir` follows h265's reading of the axis (`transform.go:80-104`: axis 0 swaps top and bottom), so the copy matches what h265 would show.
- **`CGO_ENABLED=0`**: no cgo file (`go list -f '{{.CgoFiles}}'` empty for `heic` and `hevc`); Go assembly (NEON on arm64, `hevc/*_arm64.s`, `heic/color_arm64.s`), pure Go with `-tags noasm`; `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build ./...` passes.
- **Memory model**: plain Go heap, no WASM (no `wazero`, imports are the standard library and `hevc` only). `Options.ToYCbCr` returns an `*image.YCbCr` that aliases the decoded planes (`heic/image.go:111-160`), 1.5 bytes a pixel in 8-bit 4:2:0; the default NRGBA output adds 4 bytes a pixel. Measured on a 48 Mpx `sips` HEIC: 329 MB of resident memory through NRGBA (beyond the 256 MiB limit), 131 MB through `ToYCbCr`. Above 8 bits, `ToYCbCr` is ignored and the output is NRGBA64 (`image.go:114-116`), 8 bytes a pixel. `DefaultFrameSizeLimit` is 16384² pixels (`heic.go:96`); `Options.Threads` 0 means `GOMAXPROCS`, 2 in the child (`:130-133`).

**As implemented (slice 3)**, additions and deviations:

- HEIC is decoded by `heic.DecodeColor(…, heic.Options{ToYCbCr: true, FrameSizeLimit: max_pixels})`, not through `image.Decode`. The frame limit makes the ceiling hold for the coded frames too: a hostile file whose header declares a small image over a huge frame is refused by the decoder before it allocates. h265 gives the same `ErrUnsupported` for that limit and for an unsupported feature, so the reason is `undecodable`, not `too_many_pixels` (both send the item without image); a test patches the `ispe` of a fixture to prove it. The Y′CbCr planes are converted by the box step with the matrix and range the file declares (`ColorInfo`: 1 → BT.709; 2 unspecified, 5, 6 → BT.601, as h265 does, `heic/color.go:138-140`; 4 → FCC; 7 → SMPTE 240M; 9 → BT.2020 non-constant luminance; limited or full range), since `image.YCbCr` would read them as full-range BT.601 (`heic.go:126-128`); a test checks the copy against h265's own NRGBA conversion. Any other matrix (0 identity/GBR, 8 YCgCo, 10 and 12–14 constant luminance or ICtCp, reserved codes) is `undecodable`: the item goes without image rather than with wrong colours. A monochrome HEIC (`*image.Gray`) goes through the same converter, so a limited-range grey is expanded; a HEIC with alpha (`*image.NYCbCrA`) is converted pixel by pixel, then weighed by its alpha and flattened on white. An ICC profile (Display P3) is ignored: such a photo comes out slightly less saturated. A HEIC above 8 bits takes 8 bytes a pixel: one of 48 Mpx exceeds the child's limit and is sent without image (`too_large`).
- A lossy WebP (`VP8 `) comes out of `golang.org/x/image/webp` as an `*image.YCbCr` (or `*image.NYCbCrA` with alpha) in limited-range BT.601 (RFC 6386, libwebp's `VP8YUVToRGB`), which the type does not say: the copy converts it as such (a full-range reading lost about 14 % of contrast, red (238, 17, 15) instead of dwebp's (255, 0, 2)); a test compares the fixture's quadrants with `dwebp` 1.6.0 within 3. A lossless WebP (`VP8L`) is NRGBA. JPEG and PNG greys stay full-range BT.601 (JFIF).
- The `irot`/`imir` reader reads 32-bit box sizes only: a `meta` box after a 64-bit or open-ended box gives no turn (the image is still sent). It reads at most the first 64 top-level boxes and a `meta` box of 1 MiB.
- The EXIF reader gives no orientation for an IFD0 whose entry count runs past the block, for an orientation tag that is not one `SHORT`, and for an APP1 segment longer than the file; it walks at most 64 segments before the scan.
- The box step keeps partial blocks at the right and bottom edges (`ceil(w / k)`), nothing is cropped; it flattens transparency on white (premultiplied average plus the white the alpha lets through), so the result is always an opaque `*image.RGBA`.
- The request carries two more fields, `max_output` and `memory_limit` (bytes), so that tests can lower them (a copy test runs the real child at 16 MiB); the child refuses any value above its constants (`ExitInput`, hence `copy_failed`). The child stops writing at `max_output` and answers `too_large`, so its reasons are `ok`, `too_many_pixels`, `undecodable`, `too_large`; `peak_bytes` is in the answer.
- Parent API: `imagecopy.NewCopier(argv, Limits)` (`DefaultLimits()` for production; a timeout of zero or less becomes the 30 s constant: a copy is always bounded) and `(*Copier).Copy(ctx, asset, out *os.File) (Result, error)`, `Result{Reason, Width, Height, Size, PeakBytes, MaxRSS}`. `out` is truncated and rewound before the child (its offset is shared with descriptor 4) and again after any outcome but `ok`, so it holds exactly `Size` bytes of JPEG or nothing; the caller reads it through the read-only end of `TempDir.NewFile()`. Errors: `ErrStopped`, `ErrUnavailable` (also for a copier without a child, `NewCopier(nil, …)` or a zero `Copier`), or the error of `out`, naming no file. `out` must be open for reading too (the write end of `NewFile` is read-write): as a defence in depth, the parent reads the header of the copy (`jpeg.DecodeConfig`, header only) and requires the size the child announced, else `copy_failed`. Mapping: `ErrTimeout` → `timeout`, `ErrMemory` → `too_large`, `ErrFailed`, an overflowing or unknown answer, an empty output, an output above 5 MiB or dimensions beyond the long edge → `copy_failed` (`too_large` for the size); `asset_missing` is the reason of the analysis, which opens the stored file.
- `cmd/hippo` dispatches `copy-image` right after `extract-page`, before configuration; its test runs the copier against the test binary, whose `TestMain` calls `main`.
- Fixtures: `backend/testdata/images/{rotated.heic, grid.heic, quadrants.webp}` (929, 3 600 and 1 032 bytes) made by `sips` and `cwebp` from `backend/testdata/images/synthetic.go`; `rotated.heic` keeps the Exif item `sips` copies, holding only orientation 6 (the copy never reads a HEIC's Exif). The other cases are built by `internal/capture/imagetest` (`EXIF`, `WithEXIF`, `WithSegment`, `JPEGDeclaring`, `JPEGCut`, `PNGWithAlpha`, `Quadrants`, `QuadrantJPEG`).

**Measures (task 3.9, 2026-11-06, darwin/arm64, Apple M4 Max, `BenchmarkCopyInChild`, child spawn included; synthetic images with noise, so every coefficient is decoded):**

| Image | Peak held by the child's runtime | Resident peak | Time | Copy |
| --- | --- | --- | --- | --- |
| JPEG 12 Mpx, 4032 × 3024 | 41 MB | 44 MB | 0.33 s | 792 KB |
| PNG screenshot, 1290 × 2796 | 37 MB | 40 MB | 0.06 s | 203 KB |

The PNG is the heaviest case (4 bytes a pixel); a 16-bit PNG of that size exceeds the limit and goes without image. Two more 48 Mpx cases exceed the limit and go without image (`too_large`), measured the same day: a **progressive JPEG** (made by `jpegtran -progressive` from a `sips` JPEG), whose decoder allocates its coefficients up front, 256 bytes per 8 × 8 block and component, so the child exits at once (6 ms, 12 MB resident: the allocation is seen before it is touched; about 30 Mpx at most fit in 4:2:0); and an **interlaced PNG** (`ffmpeg -flags +ildct`), which holds its passes beside the image (241 MB resident when stopped, after 0.98 s). ### D11. Private-item guarantee (RG-12, ADR-0023)

Four layers, each tested:

1. Selection: `is_private = 0` in `AnalysisQueue`.
2. The request builder returns `ErrPrivateItem` for an item with `is_private` set; the user's pass then stops, nothing is submitted nor sent, an error is logged (fail closed: a bug here blocks analysis rather than leaking).
3. The submission transaction re-reads `is_private` under `BEGIN IMMEDIATE`; an item checked Privé since the selection is not moved and stays `extracted`.
4. The body is assembled from the ids the transaction moved, so the segment of an item made private before the transaction never leaves (D6).

After the transaction the item is `submitted`; checking Privé then keeps `submitted` and its batch (RG-14 clarified; `SetPrivate` already never touches `status`; E3-02 applies the result). Tests: private items at every status never appear in any byte of any recorded body (ids, titles, notes, contents); an item made private between selection and transaction (a test hook of the pass options runs `SetPrivate` there); the builder refuses a private item.

### D12. User isolation (RG-90) and budget (RG-81)

- Every new store function takes `userID` and filters by it: selection, categories, batches, submission (`WHERE user_id = ?` on every `UPDATE`), month spend, pending rows. `content_types` is the only table read without `user_id`: it is shared by design (ADR-0022), not a business table of a user.
- `items.category_id`, `items.batch_id` cannot get a composite foreign key through `ALTER TABLE`; the store writes `batch_id` only with a batch of the same user (same transaction), and a category only through functions that check `categories.user_id` (none writes it in E3-01; E3-02 will).
- Test with two users: each batch holds only its user's items, each référentiel only its user's categories, one user's spend or pending batch never blocks the other.
- Budget: D3, checked before building; tests for reached, just below, previous month, Paris month boundary, other user.

### D14. Shared child-process package (`internal/childproc`)

Moved without behaviour change (add → migrate → remove, each step green):

## Risks / Trade-offs

- [Request format checked only against our reading of the API] → unit tests assert every field; the Message Batches API reports an invalid request in its results, not at creation, and such requests are not billed; the guard then blocks further batches until E3-02. First production night watched in the Anthropic console (to confirm with Ghislain).
- [SDK buffers or retries the raw body] → task 5.1 verifies in the installed source; fallback to `net/http` in the same package.
- [`gen2brain/h265` lacks HEIC grids or orientation] → task 3.2 before code; stop on mismatch; JPEG is what the app sends. Settled: grids decoded, `irot`/`imir` read in-house (D10).
- [Image child above budget for a 48 Mpx image] → task 3.9 and 6.6 measure; ceiling lowered to 40 Mpx with the measure recorded; worst case the child is killed and the item goes without image.
- [Ambiguous reconciliation] → at most one double send per row, logged `possible_double_send`; cost bounded by one night's batch.
- [An unknown outcome delays the user's items by a night] → only after a timeout or crash during the send; accepted to avoid double sends.
- [Seeding advances `sync_sequence` 24 times per user] → harmless (relative comparisons only; checked).
- [The API may downscale a 1568 × 1176 copy further (its pixel budget is about 1.15 Mpx, unverified)] → no correctness impact; the 1568 px long side is the spec's decision.
- [Prompt caching below the model's minimum cacheable length] → no cost, only no gain (README already says so).
