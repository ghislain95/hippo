# Design

## Context

See proposal.md for the motivation and the decisions already taken with Ghislain (schedule in Paris time, image copy, 384 MiB container, guards, submission protocol, tables). This design settles how they are built.

Current state that shapes the approach:

- Items stop at `extracted` (`internal/extraction`). The only background task is the extraction worker, started and stopped by `cmd/hippo` with its own context (`backend/cmd/hippo/main.go`).
- Heavy parsing already runs in a child process of the same binary (`hippo extract-page`, `internal/extraction/child.go`): memory watch through `runtime/metrics`, exit code 86 above the limit, explicit environment (`GOMAXPROCS=2`), `Pdeathsig` on Linux, output bounded by `cappedBuffer`, a PDF handed as descriptor 3. The image copy needs the same machinery.
- `DATA_DIR/tmp` (`extraction.TempDir`) creates files whose name is removed at once (two descriptors, one read-only) and sweeps leftovers at start-up.
- `assetfs.Dir.Open(rel)` opens a stored image through `os.Root`; `assetfs` is a leaf imported only by `httpapi` and `cmd/hippo`.
- `store.createUser` runs on a `*sql.DB` or a `*sql.Tx` (`execer`); `CreateUser` is called by tests only, `EnsureSingleUser` by `cmd/hippo`. `nextChangeSeq` is the only writer of `sync_sequence`.
- `internal/analysis/schema` embeds the bundled `classify_item` schema, generated by `cmd/schemabundle` (`x-schema-version` 1 at its root). `system-prompt.md` holds the fixed part (prompt version 3) and the formats of the référentiel and of the item message; nothing in the backend reads it yet.
- `config.Config` already has `AnthropicAPIKey` (optional), `AnalysisModel`, `BatchSchedule` (unvalidated string), `MonthlyBudgetUSD`. `capture.LoadParis` loads Europe/Paris from the embedded tz database.
- `anthropic-sdk-go`, `golang.org/x/image` and `github.com/gen2brain/h265` are approved (proposal, 2026-11-06) but none is in `backend/go.mod` yet. `golang.org/x/image@v0.47.0` is in the local module cache (indirect); the two others are not, so every claim about them below is **unverified** and has a verification task. (Slice 3: `golang.org/x/image` v0.47.0 and `github.com/gen2brain/h265` v0.2.4 are now required and verified in D10; slice 5: `github.com/anthropics/anthropic-sdk-go/v2` v2.7.0, verified in D9.)

## Goals / Non-Goals

**Goals:**

- One pass per Paris date that sends each user's waiting items in one Message Batches batch, with the guards, the request format and the private-item guarantee of the specs.
- Bounded memory: the parent never holds a batch body; one image decoded at a time, in a bounded child.
- No double send except one documented, logged case.
- The child-process code shared without changing the extraction's behaviour.

**Non-Goals:**

- Anything E3-02 to E3-08 owns (proposal, Non-goals). In particular no store function writes `cost_usd` or tokens: tests that need them use a `storetest` SQL helper, like `SetAnalysisState`.
- Validating `BACKUP_SCHEDULE` (E6 owns the backup).
- The normalised-name index of categories (E3-03), the depth check of a category written by the user or the AI (E3-03, E4).

## Decisions

### D1. Daily schedule in Paris time (`internal/schedule`)

- `ParseDaily(expr) (Daily, error)` accepts exactly five space-separated fields `M H * * *`, `M` in 0–59 and `H` in 0–23 as plain decimal integers; anything else (lists, ranges, steps, names, a non-`*` day, month or weekday field, six fields) is an error. `config.Load` calls it, so an invalid `BATCH_SCHEDULE` stops the start-up with an error naming the variable; `Config.BatchSchedule` becomes a `schedule.Daily`.
- `Daily.RunAt(date, loc) time.Time` gives the single run instant of a Paris calendar date:
  - the earliest instant whose wall clock in `loc` is that date at `H:M` (in the autumn overlap, the first of the two, CEST);
  - when no such instant exists (spring gap), the first instant of that date whose wall clock is after `H:M`, which is the end of the gap (03:00 CEST).
  - It does not rely on `time.Date` for this: Go documents that in a transition « it does not guarantee which » instant it returns (`$GOROOT/src/time/time.go:1726-1734`, go1.27.3). `RunAt` checks the candidate and its neighbours one hour apart and picks by the rule above.
- `Daily.Next(after, loc)` is the first `RunAt(d)` strictly after `after`, for `d` = the Paris date of `after`, then the following dates. Each date has exactly one instant, so the overlap never runs twice, even across a restart, and a restart never catches up a missed date (Non-goal).
- `Run(ctx, daily, loc, clock, pass)` loops: compute `Next(clock.Now())`, wait on `clock.After(next − now)` or `ctx.Done()`; on wake, if `clock.Now()` is still before `next` (wall clock moved back), wait again; otherwise run `pass(ctx)` synchronously and loop from `Next(next)`. The clock is an interface (`Now`, `After`), real in production, fake in tests that fire it explicitly (no sleep, docs/dev/testing.md « Horloge »).
- `cmd/hippo` starts `Run` in a goroutine with its own cancellable context, like the extraction worker, and waits for it before closing the store. A pass interrupted by the stop is handled by D7.
- Alternatives rejected: a cron library (new dependency for one daily form; no control of the DST rule); `TZ`-driven local time (the distroless image has no zone database; the domain already uses `LoadParis`); remembering the last run date in memory or in the base (unnecessary once each date has a single instant).

**As implemented (slice 6)**, additions and deviations to D1 and D16:

- `schedule.Daily{Hour, Minute}`, `ParseDaily`, `Daily.String()` (`"M H * * *"` without leading zeros, logged at start-up). The fields are separated by exactly one space; each number has one or two ASCII digits (`05` accepted; signs, three digits, tabs, double or edge spaces refused). `config.Load` wraps the error as `BATCH_SCHEDULE: schedule "…": …`; `BACKUP_SCHEDULE` stays an unvalidated string (Non-goal).
- `RunAt(year, month, day, loc)` takes the date as three values rather than a `time.Time`, so that no zone is implied. It examines the instants 15 minutes apart within 3 hours of the `time.Date` candidate: the earliest whose wall clock is the date at `H:M` wins; in a gap, the end of the gap is found as the start (`Time.ZoneBounds`) of the zone in effect after it. Checked at go1.27.3: `time.Date` alone returns the second occurrence in the autumn overlap (01:30 UTC for 02:30 on 31 October 2027) and 03:30 in the spring gap, so the probing is needed (a mutation that returns the candidate fails the 28 March and 31 October tests).
- `Run(ctx, daily, loc, clock, logger, task func(context.Context))`: the task returns nothing; `cmd/hippo` logs the pass's error. **Late wake-up** (review of slice 6, decided by the main session): a timer of the system does not count the time the NAS was suspended (`CLOCK_MONOTONIC` on Linux), and a wall clock can jump ahead; a wake-up more than `schedule.LateTolerance` (10 minutes) after the planned instant does not run the pass (it would run at any hour, a catch-up RG-30 forbids): it logs at warn `outcome=missed_run` with `planned` and `woke` (UTC instants, nothing else) and waits for `Next(clock.Now())`. A wake-up within the tolerance runs. After a task, the next run is `Next(max(next, clock.Now()))`, so that a clock moved back during the pass never runs a date twice. A cancel seen as the timer fires runs nothing. `schedule.SystemClock` is the real clock; `schedule/scheduletest.Clock` is the fake one (`Wait` returns the deadline of the next `After`, `Set` moves the clock and fires the timers due, `Fire` fires them without moving it). The scenarios of 6.3 set `time.Local` to Asia/Tokyo rather than `TZ=UTC` (`time.Local` is read once at start-up, so `t.Setenv("TZ", …)` proves nothing); a mutation reading `time.Local` in `RunAt` fails all four.
- `cmd/hippo`: `prompt.Load()` right after the configuration (an error stops the start-up); `newAnalyzer` returns a nil interface without `ANTHROPIC_API_KEY` and logs at warn « no ANTHROPIC_API_KEY: the nightly analysis sends nothing »; `startAnalysis(ctx, analysisOptions)` (`cmd/hippo/analysis.go`) builds the **one** `analysis.Pass` of the process, starts its `Reconcile` and `schedule.Run` in two goroutines under one cancellable context, logs `analysis scheduled` with `batch_schedule`, `time_zone` and `next_run` (UTC), and returns a `stop` deferred after the temporary directory is opened, so it returns before the temporary directory, the images and the store are closed. Tests: the reconciliation and the scheduled pass share the instance (a pass that would list while the start-up list is held fails it; a mutation building two instances fails it), `stop` waits for a pass in flight, without a key the scheduled pass runs and logs `no_api_key`, `run` starts and stops without a key, starts with a key without logging it, and refuses a schedule that is not daily.

### D2. Selection

- Users come from `store.UserIDs`; everything below is per user, every query filtered by `user_id` (RG-90).
- `store.AnalysisQueue(ctx, userID, limit)` returns (as `[]store.AnalysisQueueItem`) at most 200 items with `status = 'extracted' AND is_private = 0 AND deleted_at IS NULL`, `ORDER BY id` (ULIDs from the store clock: creation order, and the order E3-02 retries keep). It returns what the message needs except the content (kind, url, site, title, extraction mode, truncation, note, `incomplete_retried`, `is_private`, assets); the content is read per item with the existing `ItemContent` while the request is written, so only one content is in memory at a time. New index `items_user_status ON items (user_id, status, id)`.
- 200 MiB body cap (209 715 200 bytes; the API's 256 MB limit, unverified at the SDK version, under either reading of « MB »): each request is appended to the segment file (D6); when the file would pass the cap, it is truncated back to the previous request and the selection stops there. The item left out stays `extracted`, as does every later one. The cap is a field of the pass options so a test can lower it (spec scenario « Beyond the body limit »).

### D3. Guards, in this order, before any read of item content

1. No `ANTHROPIC_API_KEY` → `cmd/hippo` builds no `Analyzer`; the pass logs `reason=no_api_key` once per pass and stops. Reconciliation is skipped too.
2. Reconciliation of the user's `pending` batches runs (D8), then `store.HasBatchWithoutCost(ctx, userID)`: a batch of the user with `status IN ('pending','in_progress')` or `status = 'ended' AND cost_usd IS NULL` → `reason=cost_pending`. `failed` batches never block: nothing was billed, except the ambiguous reconciliation case (Risks).
3. `store.MonthSpend(ctx, userID, from, to)`: `SUM(cost_usd)` of the user's batches with `created_at` in `[from, to)`, the bounds being midnight of the first day of the current and next Paris month, converted to UTC. `spent >= MonthlyBudgetUSD` → `reason=budget_reached`. A batch counts in the month it was **created** (sent), not the month it ends. The comparison is the same as RG-81's (`>=`), so a budget of 0 never sends.

Each refusal logs `user_id`, `reason`, and the count of waiting items only (no content). The check happens before the batch is built: no image is decoded for a pass that will not send.

### D4. Request format

The body is the Message Batches create body `{"requests":[{"custom_id":…,"params":{…}}]}`, written by `internal/analysis` itself with `encoding/json` (`SetEscapeHTML(false)`, so `<element>` stays readable and short), never through SDK types: the request bytes are ours, testable without the SDK, and streamed (D9).

`params`, keys in this order (the cache prefix is tools → system → messages; key order in JSON does not matter to the API, it only keeps the body readable):

- `model`: `cfg.AnalysisModel`.
- `max_tokens`: 4000, or 8000 when `incomplete_retried = 1` (RG-36).
- `tools`: one tool `{"name":"classify_item","description":<root description of the bundled schema>,"input_schema":<bundled schema as embedded, without its `$schema` keyword nor any `x-*` keyword>}`. The API only promises « a JSON Schema object » for `input_schema`, so the dialect keyword and Hippo's extension keywords (`x-schema-version`, at the root and in each fiche schema of `$defs`) are left out, recursively; everything else (`$defs`, `$ref`, `title`, `description`, every constraint) keeps its meaning (decided by the main session, 2026-11-06, slice 5). Only keywords are removed: a property or definition named `x-…` and the data of `enum`, `const`, `default`, `examples` stay (`prompt.ToolSchema`, unit-tested). The envelope version is still read from the embedded bundle.
- `tool_choice`: `{"type":"tool","name":"classify_item"}`.
- `system`: two text blocks: the fixed part; then the référentiel with `"cache_control":{"type":"ephemeral"}`.
- `messages`: one `user` message (D5).

`custom_id` = item id (26-character ULID; the API's `custom_id` pattern is unverified, a test asserts the ULID alphabet fits `^[a-zA-Z0-9_-]{1,64}$`).

**Fixed part and prompt version.** `go:embed` cannot reach `docs/`, so `cmd/schemabundle` gains `-prompt <system-prompt.md> -prompt-out <file>` and writes `backend/internal/analysis/prompt/prompt.gen.json`: `{"prompt_version": 3, "fixed": "<the text of the first ```text fence under ## Partie fixe>"}`. The version is read from the `prompt_version = N` of the header line. The tool fails when either is missing or when there is not exactly one fence in that section. `-check` covers it like the bundle; the file joins `GENERATED`; its name ends in `.gen.json`, so the protect-files hook refuses a hand edit. Envelope version: `x-schema-version` at the root of the embedded bundled schema, read at start-up (start-up fails if absent). Alternatives rejected: a copy of the prompt in Go source (drifts silently); reading `docs/` at run time (not in the image).

**Référentiel** (built once per batch, per user, from `store.ContentTypes` and `store.Categories(userID)`):

```
<referentiel>
<types>
tech_article | Article technique
…
</types>
<categories>
1 | Dev | active | Développement logiciel : …
2 | Dev › Java & Spring | active |
…
</categories>
<tags>
</tags>
</referentiel>
```

- Types: non-deleted, `ORDER BY id` (ids 1–7 seeded in the §7 order); a proposed type gets ` | proposed`.
- Categories: non-deleted rows of the user (`store.Categories` returns them `ORDER BY id`; the builder makes the tree); roots `ORDER BY id`, each followed by its children `ORDER BY id`; path `parent › child`; status `active` or `proposed`; description empty when NULL, the line then ending with `|` (no trailing space). A child whose parent is deleted is not listed (cannot happen before E4; stated so the order stays total).
- Tags: empty block until E3-04. Newlines inside a name or description are replaced by a space so that one category stays one line.

### D5. The item message

One `user` message. For a link or a note, a single text block: the `<element>` block, then, when there is content, `\n<contenu>\n…\n</contenu>`. For an image, a text block with the `<element>` block, then one `image` block per asset (base64, `image/jpeg`), or none when the copy failed (D10).

`<element>` lines, in the order of `system-prompt.md`, absent fields left out:

| Line | link | note | image |
| --- | --- | --- | --- |
| `forme:` | `link` | `note` | `image` |
| `url:` | captured URL without its user info (`user:password@` removed, as the extraction does before its request); never the normalised URL | — | — |
| `site:` | `site_name` when set | — | — |
| `titre_original:` | `title` unless it equals the provisional title of the URL (RG-26, `capture.ProvisionalTitle`, exported rather than copied) | — | — |
| `extraction:` | `complète` (`full`), `repli sur les métadonnées` (`fallback`) | `aucune` | `aucune` |
| `contenu_tronqué:` | `oui` / `non` | — | — |
| `note_de_capture:` | `user_note` when set | — (the note text is the content) | `user_note` when set |
| `<contenu>` | `content_text` when set and non-empty | `user_note` (the note text) | — |

The label for `none` is `aucune`, without the « (image ou note) » of the format's comment, which describes when it applies. A multi-line note de capture stays as is, last line of the block. The prompt treats everything in `<element>` and `<contenu>` as data (prompt injection case of the eval set); the backend does not escape tags. An image's provisional title is not sent: it comes from the capture note or the date (RG-26), both already known to the AI; the proposal's « title and capture note » is the `<element>` block.

### D6. Building the body: segments, then the committed body

1. For each selected item, in order, the request JSON is appended to a **segment file**; its offset and length are kept in memory (`custom_id → [off, len)`). Text parts are marshalled; the image data is streamed from the image copy through a `base64.NewEncoder` into the file, never held whole. The 200 MiB cap is checked after each request (D2).
2. The submission transaction (D7) returns the ids it actually moved to `submitted`.
3. The **body file** is assembled from the segments of exactly those ids: `{"requests":[`, segments joined by `,` with `io.Copy` from an `io.SectionReader`, `]}`. Its size is known for the `Content-Length`.

Both are unnamed files of `DATA_DIR/tmp` (`TempDir.NewFile()`, exported by `extraction`; consumed by `analysis` through a one-method interface), so a crash leaves nothing on the NAS nor in the backups. They are closed when the send returns. Disk: at most twice 200 MiB for a moment; a write error (full disk) aborts the user's pass before the transaction, nothing is submitted, `reason=storage_unavailable`.

Why segments and a second file rather than building after the transaction: building is the slow part (image copies, seconds each); the transaction must be short and must be the last word on privacy (D11). Rejected: building the body after the transaction (items `submitted` for minutes while images decode; a crash then leaves `pending` batches for nothing); rewriting in place (no gain).

**As implemented (slice 4)**, additions and deviations to D4–D6:

- `cmd/schemabundle` requires `-prompt` and `-prompt-out` with its other flags (one generator run covers the three outputs, `-check` included). The version is the single `` `prompt_version = N` `` of the header (the text before the first `## ` heading): none or two fail. The « Partie fixe » section runs to the next `## ` heading; it must hold exactly one fence, opened by ```` ```text ````; a fence of another language, an unclosed fence (a new fence opening inside it) or an empty text fails. The fixed part is the lines between the fence lines, without the last line break. The file is written with `SetEscapeHTML(false)` and two-space indent.
- `internal/analysis/prompt.Load() (Prompt, error)` returns, from the embedded files, `Version` (3), `Fixed`, `EnvelopeVersion` (`x-schema-version` of the embedded bundle, 1), `ToolDescription` (the root `description` of the bundle) and `InputSchema` (the bundle as embedded); a missing version, fixed part or description is an error, for `cmd/hippo` to stop at start-up (slice 5). In the body, `encoding/json` compacts the schema (a `json.RawMessage` is compacted when encoded): the same JSON value as the embedded file, not the same bytes.
- Request writer: `analysis.NewRequests(RequestsConfig{UserID, Model, Prompt, Referentiel, BodyLimit, Contents, Assets, Copier, Temp, Logger})`, then per item `Add(ctx, item) (added bool, err error)`, `IDs()`, `ImagesWithoutCopy()`, `WriteBody(dst, ids) (size, error)`, `Close()` (idempotent). `added == false` with a nil error means the request does not fit: the selection stops there. Errors: `ErrPrivateItem` (checked first, before any read), `ErrCopierUnavailable` (wraps `imagecopy.ErrUnavailable`), `ErrItemGone` (the item was deleted since the selection, `ItemContent` answers `ErrNotFound`: the pass skips it and goes on), a storage error (`storage_unavailable`), or the context's. Every error names the item id at most.
- The byte limit applies to the **assembled** body, its `{"requests":[`, `]}` and commas included, so a body of the moved ids is never above it. It is checked while the request is written (a writer that refuses the byte beyond the room left), not after; a request that does not fit, or fails, is truncated off the segment file. The segment offsets are the only reference to the file, so a leftover could not reach a body anyway.
- The `tools`, `tool_choice` and `system` bytes are marshalled once per batch and copied into each request, so they are byte-identical. The message content is an array: one text block, then the image blocks.
- The image copy file (`TempFiles.NewFile`) is created at the first image of the batch, reused for each image (the copier truncates it), and read back through its read-only end with an `io.SectionReader` into a `base64.NewEncoder`. A stored file that cannot be opened gives `asset_missing` without logging the error (it names the path). The log line of an image without copy carries `user_id` too; it is written, and the image counted in `ImagesWithoutCopy`, only once the request is kept: a request that does not fit leaves neither.
- Item message: `site` and `titre_original` are written on one line (line breaks become spaces), like the référentiel's names; the note de capture stays as written. The credentials are removed by cutting only the `userinfo@` segment out of the captured string (the authority after `//`, up to the first `/`, `?` or `#`, cut after its last `@`, as `url.Parse` reads it): the rest is sent byte for byte, never re-serialised by `url.URL.String`, which would change escapes or drop an empty `#`; the result is parsed again and not sent if it still holds user info. A link whose URL does not parse (cannot happen after capture) gets no `url:` line; a link whose `extraction_mode` is unknown gets no `extraction:` line; an item of an unknown kind is refused (error, fail closed). An empty capture note or content is left out like an absent one.
- Référentiel: a description made only of blanks is written as none (the line ends with `|`); a category whose parent is not a listed root (deleted parent, or a third level) is not listed.

### D7. Submission protocol

1. Build segments (D6).
2. `store.SubmitBatch(ctx, userID, NewBatch{Model, PromptVersion, EnvelopeVersion}, ids)` in one `BEGIN IMMEDIATE` transaction:
   - re-reads `status`, `is_private`, `deleted_at` of each id **for this user**; keeps those still `extracted`, public and not deleted;
   - none kept → no row, returns empty (nothing is sent; no call is made, RG-31);
   - inserts `batches` (`id` ULID from the store clock, `status='pending'`, `item_count` = kept count, `created_at`);
   - for each kept item, `nextChangeSeq` then `UPDATE items SET status='submitted', batch_id=?, updated_at=?, change_seq=? WHERE user_id=? AND id=?`.
3. Assemble the body (D6) from the moved ids. Then leave out the items checked Privé since the transaction (Ghislain, 2026-11-06, Q1 option A, replacing the cancellation of the whole batch decided at the slice 5 review), in a loop: `store.DropPrivateFromBatch(ctx, userID, batchID) (dropped, remaining []string, err)`, in one `BEGIN IMMEDIATE` transaction filtered by `user_id`, moves each such item back to `extracted` with `batch_id = NULL`, a new `updated_at` and `change_seq` (attempts unchanged), and sets the row's `item_count` to the remaining ids, which it returns in submission order; the body file is truncated and assembled again from the segments of exactly those ids (the segment file is still open), so `item_count` is the number of requests sent by construction (the reconciliation relies on it). The loop goes on until a round leaves nothing out, so an item checked Privé during a rewrite is left out too; it ends without a cap, since each round that goes on leaves out at least one item of a batch of at most 200, and a batch left empty is failed. When no item remains, the same transaction fails the row (`item_count` is 1 to 200, so it keeps its count) and nothing is sent. Each round that leaves items out logs a warn line `outcome=private_after_submit` with `removed` and `remaining` only. A rewrite that fails puts the items back (`storage_unavailable`); a context error of `DropPrivateFromBatch` is a stop. Then, right before the send, check that the pass is not stopped (stopped → `FailBatch`, nothing sent, `outcome=stopped`, rather than a reconciliation reporting a possible double send), and send the body once (D9). Final order: `WriteBody` → loop [`DropPrivateFromBatch` → rewrite] → stop check → `CreateBatch`. The window left for an item checked Privé is the upload itself: checked during the send, the item stays `submitted` in its batch, whose result it keeps (RG-14).
4. Outcome:
   - **accepted**: `store.MarkBatchSent(userID, batchID, anthropicID)` sets `anthropic_batch_id`, `status='in_progress'`; a `UNIQUE` violation (the id is already recorded) is logged as an error and the row stays `pending` for reconciliation;
   - **refused** (the API answered a client error status, 4xx): `store.FailBatch(userID, batchID)`: in one transaction, every item of the user with `batch_id = ? AND status = 'submitted'` goes back to `extracted`, `batch_id = NULL`, new `updated_at` and `change_seq`, `attempts` unchanged (no attempt counted); the row becomes `failed`;
   - **unknown** (transport error, timeout, cancelled context during the send, crash, a redirect, or a server error status 5xx, 529 included: a gateway may answer so after the service created the batch, at the end of a long upload): nothing is written; the row stays `pending` and is reconciled (D8).
   Writes after the send use `context.WithoutCancel(ctx)` bounded to 10 s, as the extraction does, so a stop during the send still records an accepted batch.
- The send has its own 10-minute timeout (200 MiB at about 3 Mbit/s up).

### D8. Reconciliation of `pending` batches

Runs at start-up (in the background, after the store opens; not blocking the server) and at the start of each user's pass, only when the user has `pending` rows and an `Analyzer` exists.

- `Analyzer.ListBatches(ctx, since)` pages through the key's batches, newest first (ordering unverified at the SDK version; the loop does not depend on it: it stops at a page whose batches are all older than `since`, or after 10 pages), and returns `{id, created_at, request_count}` where `request_count` is the sum of the batch's `request_counts` (unverified field names).
- For each pending row, oldest first: candidates are listed batches with `created_at` in `[row.created_at − 10 min, row.created_at + 20 min]` (NAS clock skew, plus the send timeout), `request_count == item_count`, and not already the `anthropic_batch_id` of one of the user's rows.
  - exactly one candidate → `MarkBatchSent` (it is adopted; it leaves the pool for the next rows);
  - none, or more than one → `FailBatch`, logged at warn with `reason=possible_double_send`, `batch_id`, the count; the items go to the next pass.
- Listing fails → the row stays `pending`; the guard of D3 then blocks the user (`cost_pending`) until a later reconciliation succeeds. A list that reaches its 10 pages while there are more and its last page still holds a batch created after `since` fails too (a partial list could find « no candidate » and send again). The list is bounded to 2 minutes, retries included (`ListTimeout`), so that a stalled list never holds the pass nor the schedule.
- The candidate of a row may already be the `anthropic_batch_id` of another user's row (same key): `MarkBatchSent` then answers `ErrAnthropicBatchIDRecorded`, and the row is failed like a row without candidate (`possible_double_send`), rather than left `pending`, which would block the user for good.
- `Run` and `Reconcile` exclude each other (a mutex of the pass): the reconciliation at start-up never settles a row whose send is in flight.
- Residual risk, accepted in the proposal: a batch accepted by Anthropic but not matched (two users' pending batches of the same size in the same window; a 4xx answered after creation, which the API is not known to do) is sent again the next night: at most one double send per such row, always logged. A 5xx is an unknown outcome since the review of slice 5, so a batch created behind a failing gateway is adopted by the reconciliation. With one user in V1 and a dedicated key, the residual risk is a 4xx after creation only.
- E3-02 must ignore a result whose `custom_id` is not an item of the batch's row (note for E3-02).
- Rejected: matching by `custom_id` (results unreadable until the batch ends); never reverting (items stuck `submitted` forever); reverting at once after a timeout (a slow accepted send then doubles every time).

### D10. Image copy (`internal/imagecopy`, child `hippo copy-image`)

**Child protocol** (same rules as `extract-page`: no configuration, no base, no log, stderr discarded, environment `GOMAXPROCS=2` only):

- descriptor 3: the stored image, read-only, opened by the parent through `assetfs.Dir.Open` (consumed by `analysis` as a one-method interface; `assetfs` stays a leaf);
- descriptor 4: the write end of an unnamed temporary file (D6's `NewFile`), where the child writes the JPEG; the parent reads it back through the read-only end;
- stdin: one JSON line `{"max_pixels":…,"long_edge":1568,"quality":85}` (constants of the parent, passed so tests can lower them);
- stdout: `{"reason":"ok"|"too_many_pixels"|"undecodable","width":…,"height":…,"peak_bytes":…}`, bounded to 4 KiB.
No path crosses the process boundary. One image at a time: the pass copies images sequentially, so at most one decoded image exists on the NAS at any moment.

**In the child**, in this order:

1. `image.DecodeConfig` (the format is sniffed from the bytes; formats registered: `image/jpeg`, `image/png`, `golang.org/x/image/webp` (`webp/decode.go:303,313`, registered at `:319`, v0.47.0), HEIC through `gen2brain/h265` (`heic/heic.go:921-928`)). `width × height > max_pixels` → `too_many_pixels` without decoding. Ceiling: **50 Mpx**, which admits the 48 Mpx « HEIF Max » photos of recent iPhones; its memory is measured (task 3.9) against the 256 MiB limit below, and lowered to 40 Mpx if a 48 Mpx HEIC does not fit.
2. `image.Decode`. GIF is not registered: capture never stores GIF (RG-02, `assets.mime_type` CHECK).
3. Scale, never up: when the long side is above 1568, an in-house **integer box reduction** by `k = floor(long / 1568)` (average of `k × k` blocks, fast paths for `*image.YCbCr` and `*image.RGBA`/`*image.NRGBA`, generic `At` otherwise) when `k ≥ 2`, then `draw.ApproxBiLinear` to the exact size (long side 1568, other side rounded). Why: `draw.CatmullRom` (and every `draw.Kernel`) allocates a `[][4]float64` of `dst width × src height` (`golang.org/x/image/draw/scale.go:204-205` at v0.47.0): 303 MB for a 48 Mpx photo, 59 MB for a phone screenshot. `ApproxBiLinear` alone has no buffer but aliases beyond a factor of 2 (text in a photographed page). The box step is the anti-aliasing filter; afterwards the factor is below 2. Peak: decoded source + at most a `2×1568`-side RGBA (39 MB) + the 1568-side RGBA (10 MB).
4. Orientation, applied on the small image (cheap): JPEG EXIF `Orientation` (tag 0x0112, values 1–8) read by an in-house parser of the APP1 `Exif` segment (TIFF header, both byte orders, IFD0 only, every offset bounds-checked, 64 KiB max) — the standard decoder ignores APP1 (`$GOROOT/src/image/jpeg/reader.go:640-642`, go1.27.3); HEIC `irot`/`imir` read by an in-house bounded reader of the primary item's `pitm`/`ipco`/`ipma` (129 lines of code, under the ~150 of this design), since h265 applies them only to a full-size NRGBA image (« Verification » below). PNG and WebP: no orientation.
5. Transparency is flattened on white; the result is encoded with `image/jpeg` quality 85, which writes only DQT, SOF0, DHT and SOS segments (`$GOROOT/src/image/jpeg/writer.go:575-634`, go1.27.3): no EXIF, XMP, ICC nor comment reaches the copy.

**Limits**: child memory limit 256 MiB (soft limit 200 MiB), memory sampled every 10 ms (`childproc.GuardEvery`, not the 1 ms of `Guard`: see « Memory sampling » below), timeout 30 s, output JPEG at most 5 MiB (the API's per-image limit, unverified) else no image. Any other outcome (exit 86, timeout, crash, garbage, `too_many_pixels`, `undecodable`, oversized output, asset file missing) → the request is written without image block, logged with `item_id`, `asset_id`, `reason` (`too_many_pixels`, `undecodable`, `too_large`, `timeout`, `copy_failed`, `asset_missing`); the pass continues. A child that cannot start (binary missing, `fork` refused) aborts the user's pass before the transaction (`reason=copier_unavailable`), as the extraction leaves an item queued, rather than sending images as partial content.

**As implemented (slice 3)**, additions and deviations:

- HEIC is decoded by `heic.DecodeColor(…, heic.Options{ToYCbCr: true, FrameSizeLimit: max_pixels})`, not through `image.Decode`. The frame limit makes the ceiling hold for the coded frames too: a hostile file whose header declares a small image over a huge frame is refused by the decoder before it allocates. h265 gives the same `ErrUnsupported` for that limit and for an unsupported feature, so the reason is `undecodable`, not `too_many_pixels` (both send the item without image); a test patches the `ispe` of a fixture to prove it. - Parent API: `imagecopy.NewCopier(argv, Limits)` (`DefaultLimits()` for production; a timeout of zero or less becomes the 30 s constant: a copy is always bounded) and `(*Copier).Copy(ctx, asset, out *os.File) (Result, error)`, `Result{Reason, Width, Height, Size, PeakBytes, MaxRSS}`. `out` is truncated and rewound before the child (its offset is shared with descriptor 4) and again after any outcome but `ok`, so it holds exactly `Size` bytes of JPEG or nothing; the caller reads it through the read-only end of `TempDir.NewFile()`. Errors: `ErrStopped`, `ErrUnavailable` (also for a copier without a child, `NewCopier(nil, …)` or a zero `Copier`), or the error of `out`, naming no file. `out` must be open for reading too (the write end of `NewFile` is read-write): as a defence in depth, the parent reads the header of the copy (`jpeg.DecodeConfig`, header only) and requires the size the child announced, else `copy_failed`. Mapping: `ErrTimeout` → `timeout`, `ErrMemory` → `too_large`, `ErrFailed`, an overflowing or unknown answer, an empty output, an output above 5 MiB or dimensions beyond the long edge → `copy_failed` (`too_large` for the size); `asset_missing` is the reason of the analysis, which opens the stored file.
- `cmd/hippo` dispatches `copy-image` right after `extract-page`, before configuration; its test runs the copier against the test binary, whose `TestMain` calls `main`.
- Fixtures: `backend/testdata/images/{rotated.heic, grid.heic, quadrants.webp}` (929, 3 600 and 1 032 bytes) made by `sips` and `cwebp` from `backend/testdata/images/synthetic.go`; `rotated.heic` keeps the Exif item `sips` copies, holding only orientation 6 (the copy never reads a HEIC's Exif). The other cases are built by `internal/capture/imagetest` (`EXIF`, `WithEXIF`, `WithSegment`, `JPEGDeclaring`, `JPEGCut`, `PNGWithAlpha`, `Quadrants`, `QuadrantJPEG`).

**Measures (task 3.9, 2026-11-06, darwin/arm64, Apple M4 Max, `BenchmarkCopyInChild`, child spawn included; synthetic images with noise, so every coefficient is decoded):**

| Image | Peak held by the child's runtime | Resident peak | Time | Copy |
| --- | --- | --- | --- | --- |
| JPEG 12 Mpx, 4032 × 3024 | 41 MB | 44 MB | 0.33 s | 792 KB |
| PNG screenshot, 1290 × 2796 | 37 MB | 40 MB | 0.06 s | 203 KB |
| JPEG 48 Mpx, 8064 × 6048 | 89 MB | 91 MB | 1.10 s | 467 KB |
| HEIC 12 Mpx, `sips`, 5.8 MB | 51 MB | 53 MB | 0.54 s | 347 KB |
| HEIC 48 Mpx, `sips`, 23 MB grid | 120 MB | 120 MB | 1.91 s | 312 KB |
| PNG 48 Mpx, 8064 × 6048 (RGBA) | 206 MB | 209 MB | 0.46 s | 313 KB |

A 48 Mpx HEIC fits under the 256 MiB limit with room (120 MB): the ceiling stays at **50 Mpx** and the spec scenario « Too many pixels » is unchanged. The PNG is the heaviest case (4 bytes a pixel); a 16-bit PNG of that size exceeds the limit and goes without image. Two more 48 Mpx cases exceed the limit and go without image (`too_large`), measured the same day: a **progressive JPEG** (made by `jpegtran -progressive` from a `sips` JPEG), whose decoder allocates its coefficients up front, 256 bytes per 8 × 8 block and component, so the child exits at once (6 ms, 12 MB resident: the allocation is seen before it is touched; about 30 Mpx at most fit in 4:2:0); and an **interlaced PNG** (`ffmpeg -flags +ildct`), which holds its passes beside the image (241 MB resident when stopped, after 0.98 s). Phones write baseline JPEG and non-interlaced PNG; these cases cost a night's image, never the service. Times on the NAS (ARM) are expected several times longer; in the container (task 6.6, D15) the 48 Mpx HEIC took 13–16 s, most of it the 1 ms memory watch, to be measured on the NAS.

**Memory sampling (after task 6.6)**: each sample of the guard reads `runtime/metrics`, which stops the world for a moment; in the container (linux/arm64, `--memory 384m`), a 48 Mpx HEIC took 13–16 s with a sample every millisecond, 2.3 s with one every 10 ms (2.0 s native; on this Mac the 10 ms watch changes nothing: 1.94 s for the HEIC, 1.12 s for the 48 Mpx JPEG). With 30 s of timeout, the 1 ms watch left too little margin on a slower NAS. The image child therefore uses `childproc.GuardEvery(hard, soft, 10 ms)` (`imagecopy.watchInterval`, read by `guardOf`, unit-tested); the page child keeps `Guard` at 1 ms, so the extraction is unchanged. Cost: a child may run up to 10 ms past its hard limit before it exits; a decoded image grows by large steps that the header ceiling already bounds, and if the cgroup runs out first the kernel kills the child, which the parent sees as `copy_failed` (D15). The memory tests still stop a runaway child at 10 ms (`childproc` « memory over the limit exits 86 under a slower watch », `imagecopy` « a child over its memory limit gives too_large »). **Remaining risk**: the time on the NAS itself is not measured yet; if a 48 Mpx HEIC approaches 30 s there, the item goes without image (`timeout`), the pass goes on.

### D11. Private-item guarantee (RG-12, ADR-0023)

Four layers, each tested:

1. Selection: `is_private = 0` in `AnalysisQueue`.
2. The request builder returns `ErrPrivateItem` for an item with `is_private` set; the user's pass then stops, nothing is submitted nor sent, an error is logged (fail closed: a bug here blocks analysis rather than leaking).
3. The submission transaction re-reads `is_private` under `BEGIN IMMEDIATE`; an item checked Privé since the selection is not moved and stays `extracted`.
4. The body is assembled from the ids the transaction moved, so the segment of an item made private before the transaction never leaves (D6).
5. Right before the send, the moved items checked Privé since the transaction are left out (`store.DropPrivateFromBatch`, D7): back to `extracted` without batch, the row's count lowered, the body assembled again from the remaining ids; repeated until a round leaves nothing out, then the stop check and the send. The others are sent the same night; nothing is sent when none is left (Ghislain, 2026-11-06, Q1 option A; RG-14 as made precise). Only the upload itself is left as a window: an item checked Privé during the send keeps `submitted` and its batch.

After the send the item is `submitted`; checking Privé then keeps `submitted` and its batch (RG-14 clarified; `SetPrivate` already never touches `status`; E3-02 applies the result). Tests: private items at every status (links; notes and images extracted and submitted) never appear in any byte of any recorded body (ids, titles, notes, note texts, contents), and the image of a private item is never copied; an item made private after the submission is left out of the send, every item made private sends nothing, an item made private during a rewrite is left out too, items made private over many rounds are all left out and the others are sent the same night, an item made private during the send stays `submitted`; an item made private between selection and transaction (a test hook of the pass options runs `SetPrivate` there); the builder refuses a private item.

### D12. User isolation (RG-90) and budget (RG-81)

- Every new store function takes `userID` and filters by it: selection, categories, batches, submission (`WHERE user_id = ?` on every `UPDATE`), month spend, pending rows. `content_types` is the only table read without `user_id`: it is shared by design (ADR-0022), not a business table of a user.
- `items.category_id`, `items.batch_id` cannot get a composite foreign key through `ALTER TABLE`; the store writes `batch_id` only with a batch of the same user (same transaction), and a category only through functions that check `categories.user_id` (none writes it in E3-01; E3-02 will).
- Test with two users: each batch holds only its user's items, each référentiel only its user's categories, one user's spend or pending batch never blocks the other.
- Budget: D3, checked before building; tests for reached, just below, previous month, Paris month boundary, other user.

### D14. Shared child-process package (`internal/childproc`)

Moved without behaviour change (add → migrate → remove, each step green):

- child side: `Guard(hard, soft uint64) *Watch` (soft limit through `debug.SetMemoryLimit`, `GOMAXPROCS ≥ 2`, `runtime/metrics` watch every millisecond, `os.Exit(ExitMemory)` above `hard`), `(*Watch).Peak()`; `ExitMemory = 86`, `ExitInput = 2`;

- `extraction` keeps its request/result types, `RunChild`, reason tables and the mapping `ErrTimeout → timeout`, `ErrMemory → too_large`, `ErrUnavailable → errReaderUnavailable`, `ErrStopped → errReaderStopped`, other failures → `reading_failed`. Its test binary modes and all its tests stay as they are; `export_test.go` keeps its names as aliases.
- `cmd/hippo` dispatches `extract-page` and `copy-image` before anything else.
- The gosec G204 exclusion moves from `internal/extraction/child.go` to `internal/childproc/`; « only one file starts a subprocess » now names `childproc`.

As implemented (slice 2), additions to the list above:

- `Run` returns `(Result, error)` with `Result{Output, Overflow, ExitCode, MaxRSS}` filled whatever the outcome (`MaxRSS` from the child's rusage, normalised to bytes, 0 outside Unix: the measures of 3.9 and 6.6 use it). Every error wraps exactly one sentinel: a fifth one, `ErrFailed`, covers « other failures » (another exit code, a signal, the pipes), so callers map outcomes with `errors.Is` only (the `nilerr` linter refuses `err != nil` followed by a fallback returning `nil`). `Spec.Timeout` zero means the parent's context only.
- `Command(ctx, Spec, stdout) *exec.Cmd` is exported so that tests inspect the child (environment, descriptors, stderr) without starting it; `Run` is built on it. `(*Watch).Stop()` is exported next to `Peak()` (the child stops its watch on early returns).
- `extraction`: `pageReader.command` becomes `pageReader.spec` (returns a `childproc.Spec`); the answer is decoded by `decodeAnswer`. `export_test.go` keeps every exported name and signature, but its bodies change (they built `cappedBuffer` and `exec.Cmd` themselves); no other extraction test file changes. The measures keep running without time limit, as before.
- `(*TempDir).NewFile() (w, r *os.File, err error)`: the write end (read-write) and a read-only end, name removed before return, errors wrapping the storage error and naming no file; the unexported `create` (PDFs) is built on it. The name prefix stays `.pdf-` (it lives for an instant, and the start-up sweep removes any regular file).
- After task 6.6: the sampling interval of the watch is a parameter. `GuardEvery(hard, soft uint64, interval time.Duration) *Watch` (an interval of zero or less is `WatchInterval`); `Guard(hard, soft)` is `GuardEvery(hard, soft, WatchInterval)` with the exported `WatchInterval = 1 ms`, so the page child is unchanged. The image child samples every 10 ms (D10 « Memory sampling »). Tests: the watch takes no more samples than its interval allows (internal test of `watchMemory`), and a child guarded every 10 ms still exits 86 above its limit.

### D15. Memory budget (container 384 MiB)

| Part | Bound | How |
| --- | --- | --- |
| Service at rest, plus a pass | ~60–80 MB | measured 61.6 MB peak at rest (spec-v1, 2 November 2026); the pass holds one item's content (≤ 1 MB JSON) and the segment offsets; bodies stream from disk |
| Page child (extraction, may run during a pass) | 48 MiB | unchanged |
| Image child | 256 MiB (soft 200) | D10; one at a time; memory sampled every 10 ms (a 48 Mpx HEIC: 13–16 s in the container at 1 ms, 2.3 s at 10 ms; NAS not measured yet); measured (task 3.9, darwin/arm64) 120 MB for a 48 Mpx HEIC, 91 MB for a 48 Mpx JPEG, 209 MB for a 48 Mpx RGBA PNG |
| Sum | ~384 MiB | the limit |

No `GOMEMLIMIT` on the parent: its live heap stays small, and a soft limit near it would make the collector thrash. If the cgroup still runs out, the kernel kills the largest process, the image child, which the parent sees as `copy_failed`. Task 6.6 measures it in the container (`--memory 384m`): a pass with a 48 Mpx HEIC while a 50 MiB PDF is extracted; result recorded in `spec-v1.md`, ceiling lowered if needed.

**Measures (task 6.6, 2026-11-06, container `linux/arm64` built from the backend `Dockerfile` at ddcd23c, `--memory 384m`, Docker Desktop 28.3.2 on an Apple M4 Max, kernel 6.10 linuxkit, cgroup v2; `ANTHROPIC_API_KEY` empty, so no AI call):**

- Method: without a key the pass copies no image (guard 1, D3), so the two children of the image were driven directly inside the running container by a small static driver started with `docker exec` (scratch, not committed): `/hippo copy-image` on a synthetic 48 Mpx HEIC (8064 × 6048, 20.5 MB grid, `sips` from a Go-generated noisy PNG), its output an unnamed file of `DATA_DIR/tmp` as `NewFile` makes it, and meanwhile `/hippo extract-page` reading in a loop a synthetic PDF of 49.3 MiB (`pdftest.Large(52_000_000, 100)`, 100 pages with images), 34 to 38 readings during each copy. The server ran beside them; `/healthz` was polled from the host every 200 ms. Memory: the cgroup's `memory.peak` and `memory.events`, and `anon` of `memory.stat` sampled every 10 ms (`memory.peak` counts the page cache of the files read, which the kernel reclaims).
- HEIC 48 Mpx with the PDF, 3 rounds: anonymous memory of the container at most **214.5 MiB**, `memory.peak` at most 242.9 MiB (page cache included), `oom` 0, `oom_kill` 0, `max` 0; image child 123–129 MB held by its runtime, 144–151 MiB resident; PDF child at most 37.7 MiB resident; copy `ok` (1568 × 1176, 146 KB).
- Worst case beside it, a 48 Mpx RGBA PNG with the PDF: anonymous 288.7 MiB, `memory.peak` 376.6 MiB (page cache reclaimed at the limit, `max` events 0 to 27 by run), `oom_kill` 0; image child 231 MiB resident; copy `ok`.
- `/healthz`: 247 answers of 247 were 200 during the runs, the slowest in 19 ms; the container stayed `healthy`. `DATA_DIR/tmp` was empty afterwards.
- The 384 MiB limit holds with about 170 MiB of room for the HEIC: the ceiling stays at **50 Mpx**.
- **Time, a finding**: in the container the HEIC copy took **13–16 s** (2.0 s natively on the same Mac and file), a 48 Mpx JPEG 7.0 s (0.9 s natively). The CPU is not the cause (an integer loop runs at the same speed in the VM). The memory watch of `childproc.Guard` is: it reads `runtime/metrics` every millisecond (`watchInterval`), and the same build with a 10 ms tick copies the HEIC in 2.3 s and the JPEG in 1.1 s in the container. The cost of that tick in the Docker Desktop VM is measured here; on the NAS (bare-metal Linux, slower ARM cores) it is not, and a copy near 30 s would end in `timeout` (item without image, service unharmed). The PDF reading shares the watch and its 8 s deadline. Decided: 10 ms for the image child (D10); NAS time still to measure.

## Risks / Trade-offs

- [Request format checked only against our reading of the API] → unit tests assert every field; the Message Batches API reports an invalid request in its results, not at creation, and such requests are not billed; the guard then blocks further batches until E3-02. First production night watched in the Anthropic console (to confirm with Ghislain).
- [SDK buffers or retries the raw body] → task 5.1 verified in the installed source (v2.7.0): streamed, no retry without `GetBody`; the SDK path is kept (D9).
- [`gen2brain/h265` lacks HEIC grids or orientation] → task 3.2 before code; stop on mismatch; JPEG is what the app sends. Settled: grids decoded, `irot`/`imir` read in-house (D10).
- [Image child above budget for a 48 Mpx image] → task 3.9 and 6.6 measure; ceiling lowered to 40 Mpx with the measure recorded; worst case the child is killed and the item goes without image.
- [Ambiguous reconciliation] → at most one double send per row, logged `possible_double_send`; cost bounded by one night's batch.
- [An unknown outcome delays the user's items by a night] → only after a timeout or crash during the send; accepted to avoid double sends.
- [Seeding advances `sync_sequence` 24 times per user] → harmless (relative comparisons only; checked).
- [The API may downscale a 1568 × 1176 copy further (its pixel budget is about 1.15 Mpx, unverified)] → no correctness impact; the 1568 px long side is the spec's decision.
- [Prompt caching below the model's minimum cacheable length] → no cost, only no gain (README already says so).
