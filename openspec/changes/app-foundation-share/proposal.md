# Proposal

Backlog stories: **E5-01 — App foundation** and **E5-02 — Share extension** (opens epic E5, mobile app; decided with Ghislain on 2026-11-13 to ship them together, before the read API of E4).

Rules: RG-01 to RG-10, RG-12, RG-13, RG-15, RG-38 · ADRs: ADR-0012, ADR-0013, ADR-0014, ADR-0015, ADR-0016, ADR-0017, ADR-0023, ADR-0027, ADR-0030, ADR-0033, ADR-0034, ADR-0035, ADR-0036.

## Why

The backend captures, extracts and analyses items, and it runs on the NAS (E6), but nothing on the iPhone sends it anything: the app is a skeleton that shows the server's state, and the share extension only existed in the throwaway prototype of E1. With the foundation of the app and a real share extension, Ghislain can share links, texts and images to the real Hippo from Safari, Instagram or Photos this week; every night's analysis then has real items, before the library and the fiche (E4, E5-03, E5-04) let him read them.

## What Changes

- **App foundation (E5-01)**, reduced to what can be built before the read API (decided with Ghislain on 2026-11-13):
  - `expo-router` navigation with a root layout and a home screen, the generated API client, and the server URL and token injected at build time (already there, kept);
  - a theme: colour and spacing tokens, light and dark following iOS automatically, text sizes that follow the iOS text size setting (Dynamic Type);
  - the home screen shows the app name, the server state and a short explanation that items are captured from the share sheet; no library yet.
  - **Moved**: the accent colour per category goes to E5-03 (the categories are not served before E4), forcing light or dark goes to E5-08 (it needs the Réglages screen). The backlog is updated.
- **Share extension (E5-02)** in Swift and SwiftUI, its target generated by `@bacons/apple-targets` from `app/targets/share/` (ADR-0036; the dependency was accepted by that ADR):
  - activated for a web URL, a text or an image only (no file: a PDF shared as a file is out of V1, decided on 2026-11-13; a link to a PDF is captured as any link);
  - a small form: a preview, the note field, the Privé switch off by default (RG-10), Enregistrer;
  - **a shared text** becomes the body of a `note`, editable in the form, without a capture note field (RG-07); a text that is only an `http`/`https` URL once trimmed becomes a `link`, with the note field (decided on 2026-11-13);
  - **an image** is sent in its original format when the source app offers it (HEIC, PNG), JPEG otherwise (decided on 2026-11-13); its size is checked against 20 MB before the send (RG-02), so that a too large image is told as such and never as an unreachable server;
  - the extension sends `POST /api/items` itself, in the contract's format, with a capture id per share so that « Réessayer » never creates a second item (RG-08); a duplicate link answers the existing item (RG-04, RG-15) and the confirmation says so;
  - a visible confirmation within 5 seconds on a good network; without the server, a clear message, « Réessayer » and « Copier le lien » (RG-06).
- **Swift conventions** (decided on 2026-11-13): `swift format` (shipped with Xcode, no dependency) formats and lints the extension (`make lint-swift`, part of `make check-swift`); its pure logic (form of the capture, request body, size check, error messages) lives in a small Swift package tested by `swift test`, run in CI on a macOS runner.
- **Screens mocked up and validated** by Ghislain before they are coded (E5 rule): home, share form, sending, confirmation (new and duplicate), and the error states.

## After the adversarial pass (2026-11-13)

Decided with Ghislain:

- **Mixed shares**: one item per share, the form chosen by priority web URL > image > text; a text that comes with a URL or an image prefills the editable note field (screen 9), so that a Safari selection is never lost. RG-01 gets this rule.
- **After a `200`**: « Déjà dans Hippo » only for a link on its first send; a `200` after « Réessayer » (a replayed capture, RG-08) shows « Enregistré ». « Réessayer » sends exactly the same request; the form stays frozen after the first send.
- **New screens 9 to 12** (`mockups.md`): link with an accompanying text, refused by the server (the problem's `detail`, French, shown as is), token refused (`401`), saved as private (RG-12, RG-13). Screen 4 says « Image », screen 8 gives one decimal.

Technical decisions (session, from the pass):

- **Errors**: no answer (`URLError`) or `502`, `503`, `504` → unreachable, with « Réessayer »; `413` `image-too-large` → too large; `401` → token refused; any other `4xx` → refused, without « Réessayer »; other `5xx` → unreachable. The connection is bounded so that a NAS that does not answer is told within seconds, while the upload of a large image keeps the time it needs (the server allows 5 minutes); the exact bounds are set in the design.
- **Images**: a closed list of types in this order, HEIC > PNG > WebP > JPEG (RG-02), never « the first type that conforms to `public.image` »; an image offered only as an object or another format is converted to JPEG; the 20 MB check comes after any conversion. The image is read as a file, its thumbnail made with ImageIO, and the request sent from a temporary file, so that a 20 MB original stays within the extension's memory (~120 MB). The first task records, on the iPhone, the types Photos, Safari and the screenshot editor really offer (the prototype received JPEG only).
- **Build**: the extension's `Info.plist` is versioned (its activation rules: one web URL, one text, one image, no file); the server URL and token are written at `prebuild` by a small local config plugin into a git-ignored Swift file, and the build fails when the token is missing or the URL is not `https` for a device build; nothing in the extension logs headers or content; the token stays readable in the built app, as in the JS bundle (accepted for a personal use, ADR-0016, ADR-0027).
- **Swift layout**: `app/targets/Package.swift`, the pure logic in `app/targets/share/Core` (compiled into the extension and by SwiftPM), its tests in `app/targets/ShareCoreTests/` (outside any target folder), limited to Foundation, UniformTypeIdentifiers and ImageIO; a capture id (ULID, ADR-0035) generated in Swift without a library.
- **Checks**: `make lint-swift` and `make test-swift`, a CI job on a macOS runner (Xcode pinned, path filter on `app/targets/**`, in the `needs` of `ci-ok`, ADR-0034), a versioned `.swift-format`; the CI does not build the extension target, so a local `npx expo prebuild --clean` then `xcodebuild` for the simulator is part of the definition of done.
- **Scenarios**: the `share-extension` scenarios cover the pure logic (`swift test`), the `app-shell` scenarios the app (jest); what only a device can show (Instagram, Photos, 5 seconds, Dynamic Type in the extension) goes to the QA checklist.
- **Theme of the extension**: it follows light and dark and Dynamic Type; colours come from one JSON token file read by the app's theme and by the extension's target config.

## Capabilities

### New Capabilities
- `app-shell`: the app's navigation, build-time configuration, theme (light and dark, Dynamic Type) and home screen.
- `share-extension`: what the share extension accepts, the form it shows, the capture it sends and how it reports success and failure.

### Modified Capabilities
None: the capture contract (`item-capture`) is unchanged; the extension is one more client of it.

## Non-goals

- The library, the fiche, capture inside the app, Review, Explorer, Réglages (E5-03 to E5-08), the offline copy (E5-09) and animations (E5-10).
- Any change to the backend or to `api/openapi.yaml`.
- Sharing a file (PDF or other) from Files.
- Changing the server URL or the token without a new build (ADR-0014).

## Impact

- **AI cost**: none directly; captured items are analysed by the existing nightly batch, within the monthly budget (RG-81).
- **Private items**: the Privé switch is sent with the capture (RG-10, RG-15); nothing else changes, the backend keeps a private item away from the AI (RG-12).
- **Persisted data**: no change to the server; the extension stores nothing (ADR-0014). Original HEIC and PNG images are stored on the NAS as they are, metadata included (GPS position): RG-38 strips it from the copy sent to the AI, not from the NAS nor the backups, which grow accordingly.
- **API contract**: none.
- **Prompt and fiche schemas**: none.
- **Dependencies**: `@bacons/apple-targets`, pinned to 5.0.0 (accepted by ADR-0036); it brings the native module `ExtensionStorage`, unused, and warns at `prebuild` about App Groups, a warning never to « fix » by adding one (ADR-0013, ADR-0014). No other new package; the config plugin uses `expo/config-plugins`, already installed.
- **CI**: one more job on a macOS runner for `swift test` and `swift format lint` (free for a public repository, slower than the Linux jobs).
- **Docs**: `docs/dev/conventions-app.md` (Swift conventions), `docs/runbook-ios.md` (build and install the real app and its extension), `docs/spec-v1.md` (app section), `docs/metier.md` (RG-01 precised with the shared text rule, with Ghislain's agreement of 2026-11-13), backlog E5-01, E5-02, E5-03, E5-08.
- **ADRs**: none challenged. ADR-0030 and ADR-0033 do not list Swift; ADR-0036 already sends the Swift conventions to `docs/dev/conventions-app.md`, which is where they go.
- **User QA: yes.** On the iPhone: Safari (link, link with a selection), Instagram, Photos (photo and screenshot: format received, HEIC giving a copy at the next batch), a text from Notes, a note with a photo, a URL copied as text, two photos (no extension), a duplicate link, Réessayer after a lost answer, Privé, airplane mode, server stopped behind Tailscale (`502`), a wrong token (`401`), a too large image, dark mode and a large text size in the app and the extension, memory for a large image, SideStore install of the real bundle (2 new App IDs) and removal of the E1 app.
